# Animation spec

## Homepage conversation (`src/components/home/ConversationPlayer.tsx`)
Port of the reference sequence with anime.js v4:

1. Wait `startDelay` (CMS, default 400 ms).
2. For each bubble: show it, measure the message (capped to the viewport), fix the bubble to 0 × 2.25em, then `animate` width `0ch → 4em`, marginTop `2.5em → 0`, marginLeft `-2.5em → 0`, 800 ms, the reference's own easeOutElastic (2016 anime.js, elasticity 50: period = 95 % of duration, one slow overshoot), ported as `legacyOutElastic`. Loop scale `1.05 ↔ .95` (1100 ms, inOutQuad). Dots slide in (`translateX -2em → 0`, scale `.5 → 1`, 400 ms) and pulse (scale `1 → 1.25`, opacity `.5 → 1`, 300 ms, 100 ms stagger).
3. After the typing time (CMS override, or `characters × 20 ms + 500 ms`; `snappy` uses 10 ms per character): stop the loops, shrink the dots out (300 ms), stretch the bubble to the message size (800 ms, same legacy elastic), fade the text in (300 ms) when the dot animation passes 65 %. The previous bubble loses its squared corner; the last one keeps it.
4. Next bubble after `characters × 20 ms + random(900, 1200) ms`. If the newest bubble is below the fold the container scrolls to it (750 ms).

Fallbacks: `prefers-reduced-motion`, the Appearance "reduced" intensity, or the `instant` preset show every bubble at once. Without JavaScript the server-rendered bubbles are visible and the dots are hidden (`html.js` gate in globals.css).

## Inner pages
- React animates only the outermost page boundary on a route change, so a page leaves as one snapshot. Exits and entrances carry different classes (`nav-forward-out`/`nav-forward-in`, `nav-back-out`/`nav-back-in`) and the leaving group is painted above the arriving one (z-index 90), so the old page visibly slides away and reveals the next page, which is already in place underneath.
- Page transitions use React's `ViewTransition` (`src/components/shell/PageFrame.tsx` around every page, `transitionTypes` on links). The old and new pages animate at the same time on browser snapshots, so the screen is never empty between pages. Forward (card → project, blog list → article, home choices): the cards pull back to the left one by one (520 ms, 60 ms stagger), the visual follows after 280 ms (680 ms), the rest of the old page slides left and the new page arrives from the right (620 ms, 240 ms after the cards start). Back from a project (back link): the text column pulls out to the right first (480 ms), the hero follows after 220 ms (640 ms), and the projects page arrives from the left with its picture already present and the cards sliding in one by one. Sidebar links are forward turns too (old page out to the left, new page in from the right; a description page stages its text first, then the hero). Only the explicit back link turns the other way. The sidebar is anchored. Browser back/forward and reduced motion show no slide. Previous implementation note: on arrival the visual comes first and the cards or text follow. Everything travels left to right. First load of /projects: the left panel first (wordmark at 0 ms, nav items from 160 ms in 70 ms steps, links at 560 ms), then the visual wipes in from the left at 560 ms, then the cards slide in from the left one by one, top to bottom, from 1500 ms in 140 ms steps. Arriving by navigation: visual at once, cards from 860 ms. Project page: the hero fades and settles (720 ms), then the info column and the blocks rise in from 560 ms with 60–80 ms steps. Other pages: the photo or cover first, then each block from 520 ms. Card → project page is a forward page turn: the cards pull back to the left from top to bottom (520 ms, 60 ms stagger) while the visual slides left with them (680 ms), and the project page arrives from the right (hero clip from the right, info and blocks from +40 px). Every other navigation is a turn back:  cards and text slide out to the right in sequence (480 ms, 50 ms stagger), the visual follows 260–320 ms later, then the route changes (900 ms on the explorer, 760 ms on a project page, 520 ms elsewhere). Modifier clicks, external links, admin links and reduced motion skip it.
- Project visuals wipe in from the left edge: `clip-path: inset(0 100% 0 0) → inset(0)` over 600 ms with cubic-bezier(.77,0,.18,1), while the incoming image settles from a 6 % leftward offset. The previous visual stays beneath until the wipe completes. After settling, the visual zooms once from 1.0 to 1.08 over 14 s with a soft ease-out and stops. On a switch the outgoing visual is frozen at its current zoom (inline transform, animation removed) so it never moves under the wipe, and the incoming visual always starts from 1.0; returning to a project restarts its zoom. The stage uses the high-resolution still (3840 × 2400 JPEG), not the loop.
- Row to card, staggered and without any text resizing: the row grows from 56 to 76 px and the slate card layer fades in (320 ms); the number rolls like a clock, one step per digit (the previous digit slides up, the new one rises in, 640 ms), the first digit first and the second 160 ms later; the thumbnail squeezes from 100 px to a 6 px sliver and moves beside the large number (420 ms, from 60 ms); the small tab title fades out while the large title and category cross-fade and slide up (from 160 ms) and the accent arrow slides in (from 260 ms). Release runs the same transitions back with no delays.
- The play overlay button scales 8 % on hover; the video host is loaded only on click.
- Hover states use 200 ms colour and transform transitions. Durations scale with the Appearance speed preset (`--speed`).
- All inner-page motion is decorative and disabled under `prefers-reduced-motion`.
- No scroll-driven animation and no Three.js: nothing in the brief justified the cost.
